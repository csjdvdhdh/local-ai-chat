# مدار — استضافة بوتات Telegram ببايثون

مشروع ويب عربي لإدارة بوتات Telegram المكتوبة ببايثون. يستطيع المستخدم إنشاء حساب، رفع ملف `.py`، إدخال توكن البوت، ثم بدء الخدمة وإيقافها ومراجعة سجلاتها.

## البنية وحدود الأمان

يخدم `server.py` الواجهة وواجهات API. تُخزّن الحسابات والجلسات ومصدر البوت في PostgreSQL؛ لا يُشغّل كود المستخدم داخل عملية لوحة التحكم. ينشئ الخادم مشروع Railway وخدمة منفصلين لكل بوت. تصل شيفرة البوت إلى خدمة التشغيل عبر نقطة داخلية بتوكن خاص بها، بينما يمر توكن Telegram إلى متغير بيئة خدمة ذلك البوت ولا يحفظه تطبيق اللوحة في قاعدة بياناته. رمز Railway يبقى في خدمة اللوحة ولا يمرر إلى بوتات المستخدمين.

تُقبل ملفات Python حتى 256 كيلوبايت، وملفات `requirements.txt` حتى 8 كيلوبايت وبحد أقصى 30 اعتماداً. الحزم تُثبّت داخل خدمة البوت المعزولة. يجب أن يقرأ كود البوت التوكن من متغير البيئة `BOT_TOKEN`، وألا يضمّنه في المصدر. مثال:

```python
import json
import os
from urllib.request import urlopen

TOKEN = os.environ["BOT_TOKEN"]
with urlopen(f"https://api.telegram.org/bot{TOKEN}/getMe", timeout=20) as response:
    print(json.loads(response.read()))
```

كل خدمة بوت تتلقى ما تحتاجه من إعدادات البوت الخاص بها فقط. يجري تثبيت الحزم وتشغيل كود البوت بعد إسقاط صلاحيات العملية إلى مستخدم النظام غير المميز `nobody` داخل حاوية Railway المستقلة. يظل الكود المرفوع برنامجاً يملكه المستخدم؛ لا ترفع شيفرة لا تثق بها إلى حسابك، وراقب حدود الإنفاق. الحد الافتراضي بوت واحد لكل حساب و10 بوتات للمنصة كلها. التسجيل في Railway يتطلب رمز دعوة، ولا يتوفر في الإصدار الحالي تحقق بريد إلكتروني أو استعادة كلمة مرور ذاتية.

## إعداد Railway

اربط هذا المستودع بخدمة Railway واجعل جذر المشروع هو المستودع؛ سيُستخدم `Dockerfile` الموجود في الجذر. أنشئ قاعدة بيانات PostgreSQL في Railway واربط متغير `DATABASE_URL` بخدمة الويب. أضف متغيرات البيئة التالية إلى خدمة لوحة التحكم:

اضبط مسار فحص صحة الخدمة على `/healthz` في إعدادات Railway.

راجع [مراجع Railway API الرسمية](RAILWAY_API_REFERENCES.md) قبل منح خدمة المنصة صلاحية إدارة مشاريع Workspace.

- `DATABASE_URL`: عنوان PostgreSQL من Railway.
- `PUBLIC_BASE_URL`: رابط HTTPS العام لخدمة اللوحة، من دون `/` أخير.
- `RAILWAY_API_TOKEN`: رمز API من نوع Workspace يملك صلاحية إنشاء وحذف المشاريع والخدمات داخل مساحة العمل المخصصة للمنصة.
- `RAILWAY_WORKSPACE_ID`: معرّف مساحة العمل التي ستُنشأ فيها مشاريع البوتات.
- `PLATFORM_INVITE_CODE`: رمز دعوة عشوائي غير فارغ؛ يمنع فتح التسجيل العام غير المقيد افتراضياً.
- `PRODUCTION=true` و`COOKIE_SECURE=true`.
- `MAX_BOTS_PER_USER=1` و`MAX_TOTAL_BOTS=10` (اختياريان؛ قيمهما الافتراضية آمنة ومحدودة).

احفظ رمز Railway في إعدادات Railway فقط ولا تضعه في GitHub أو ملفات المستودع أو داخل خدمة بوت. إنشاء كل بوت ينشئ مشروعاً جديداً وخدمة جديدة في مساحة العمل، وهذا قد يستهلك موارد ويُحاسب على حساب مالك مساحة العمل. راجع الأسعار والحصص في Railway، وابدأ بحسابات اختبار وحدود منخفضة. حذف بوت من اللوحة يحذف مشروع Railway وخدماته ونشره، وهو إجراء لا يمكن التراجع عنه.

إذا لم تكتمل متغيرات البيئة، تعرض المنصة حالة الإعداد وتمنع رفع البوتات وتشغيلها. لا يمكن تفعيل الاستضافة الفعلية من المستودع وحده قبل ربط PostgreSQL وصلاحية Railway وعنوان HTTPS العام.

## تشغيل محلي للتطوير

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn server:app --reload --host 127.0.0.1 --port 8000
```

يستخدم التشغيل المحلي SQLite تلقائياً لصفحة الدخول ولوحة التحكم. إنشاء خدمة بوت فعلية يحتاج متغيرات Railway المذكورة أعلاه؛ لا تضع بيانات اعتماد إنتاجية في جهاز أو ملف غير آمن. لإنشاء ملف أسرار محلي، ابدأ من `.env.example` ولا ترفع نسخة `.env` إلى Git.

## فحوصات وبناء

```bash
python -m py_compile server.py app.py
node --check <(sed -n '/<script>/,/<\/script>/p' web/index.html | sed '1d;$d')
docker build -t madar-bot-platform .
```

خدمة GitHub Pages الثابتة لم تعد مناسبة لأن هذه الواجهة تحتاج API وقاعدة بيانات؛ النشر المقصود للخدمة الكاملة يتم عبر Railway. يبقى مجلد `mobile/` وأداة `app.py` القديمة منفصلين عن تطبيق الاستضافة.
